## 三、变更过程

### 3.1 执行步骤

1. `git diff` 确认开发者已把两条词条置 `active`，同步计数与变更记录（G-9 追加）。
2. 从 GOV-000 §5.4 F3 取九项指标原表，扣掉 R-02 已删的「盘点差异率」。
3. 先写 5 条通用口径（时区、窗口终点、有效期、排序、单位），再逐项落到公式——顺序反了会导致每项都要重复解释一遍。
4. 单独抽一节写「红冲在统计中的处理」，因为它与 `DES-001` §4.1 的结存算法**故意不同**。
5. 把两处与建表约束冲突的地方单列为待裁定，不自行拍板。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 原口径「数据完整率 = 分类、规格、单位、安全库存四项齐全」与 `DES-001` 冲突：分类与单位是 `NOT NULL`，永远齐全 | 登记为 Q-2，给三个选项；文中先按字面写，并注明偏差。不擅自改口径（属 RFC 范围） |
| P-2 | 「近 30 天」若以"当前时刻"为终点，同一天两次请求结果会变，违反 PRD US-S3 验收 1 | 取 C-2：窗口终点固定为当日 23:59:59.999，结果只随新写入变化 |
| P-3 | 统计笔数与结存求和对红冲的处理相反，容易被后来者"统一"掉 | 在 §4 末尾显式写明两处口径不同且各有依据，禁止互相统一，并在 §6 追溯里指向 DES-001 §4.1 |
| P-4 | M-4 占比之和因舍入不等于 1 | 明确不做强制配平，避免实现时加"补差到 1"的补丁逻辑 |

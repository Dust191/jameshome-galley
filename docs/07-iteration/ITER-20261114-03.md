## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净，无他人改动。
2. 先找全上一轮的落点表述，共六处：三环境表、§7.3 D5-8、§7.7 发布流水线、§7.8 的 T5-02 与 T5-10、§7.6 的性能说明。逐处改回同机口径，避免只改一处留下矛盾。
3. 把压测约束写成可执行的三条，而不是一句「注意不要打垮线上」：说明同机共享哪些资源、盯哪几个指标、停止点怎么算（阈值减 5 个百分点，逐项换算成 80%）。再加一条兜底——停止时未达到目标数据量，如实记「未测到目标量级」，不许外推。
4. `DVT-10` 上一轮的补记已写「staging 是本地虚拟机，不构成容量证明」，落点变了这句话就不成立。按「只增不删可改」追加第二条补记更正，不改前一条。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 同机压测最大的风险是压垮线上，而停止点依赖云监控采样，采样是分钟级，存在滞后 | 停止点按「阈值减 5 个百分点」而不是「到阈值才停」，留出的 5 个点就是给采样滞后与突发峰值的缓冲；`DEV-009` §7.6 写明了这一点 |
| P-2 | 同机部署两套服务，若项目名、端口、数据卷不隔离，staging 会连到生产库 | 三环境表明确「独立项目名、端口与数据卷」，并把它写进允许差异项，T5-10 同步 |
| P-3 | 磁盘上有个巧合值得说明：云监控磁盘告警是使用率 85%（剩余 15%），而 G5 运维组要求剩余空间 >20% | 停止点 80% 使用率正好等于剩余 20%，压测不会把磁盘推到违反 G5 判据的位置；这一点写进本记录，不另立条款 |
| P-4 | 上一轮已在 `DVT-10` 落了「本地虚拟机」的判断，直接改会破坏留痕 | 追加补记更正，保留原句；`ITER-20261114-02` 同样只加补记、不改正文 |

# ITER-20261112-07

这份记录回答三个问题：备份怎么从文档变成能跑的脚本、恢复凭什么算成功、过程中撞到哪些只在真机出现的坑。

## 一、为什么要先做这一步

生产库此前是**单点**：一个 Docker 卷，没有第二份。任何一次误操作、卷损坏或宿主机故障都不可逆，且 `RUN-002` 当时只有命令示例，没有可执行脚本，也没有一次真实恢复记录。按 `DEV-009` §7.6 的数据组判据，备份演练是 G5 的前置，不能留到验收当天补。

## 二、落了什么

| 文件 | 作用 |
|---|---|
| `infra/backup/backup-db.sh` | 导出 → sha256 → 上传内网 OSS → 回查大小与 MD5 → 本地按日/周/月留存 → 写日志 |
| `infra/backup/restore-db.sh` | 取备份（本地或 `oss://`）→ 校验 sha256 → 建独立目标库 → `pg_restore` → 核对 → 清理 |
| `RUN-002` | 按脚本实际行为重写 §2、§4、§5，补脚本安装步骤与安全约束 |
| `DEV-009` | §7.7 备份行、§7.8 `T5-07` 转「已完成」 |

三处设计取舍：

1. **不 source `.env.prod`**，改为按键取值。环境变量文件里有带空格的值（`GALLEY_RECONCILE_CRON`），整体 source 会被 shell 当命令执行——这不是假设，本轮真的撞上了（见 §四）。
2. **上传后必须回查**。`ossutil cp` 返回 0 只说明请求被接受；脚本用 `stat` 比对远端 `Content-Length`，并利用单段上传的 ETag 就是内容 MD5 这一点做内容级比对。
3. **恢复默认落独立库**。`restore-db.sh` 无参数时恢复到 `galley_restore_check` 并在核对后删除；目标库等于生产库时必须显式 `--confirm-production`，另拒绝 `postgres` / `template1` 作目标。

## 三、演练结果

| 项 | 结果 |
|---|---|
| 备份 | 29 KB，耗时 <1s，sha256 `e326ae20…` |
| 上传回查 | 远端 30715 B 与本地一致；ETag 与本地 MD5 一致 |
| 从 OSS 恢复 | 端到端 2 秒（下载 + 建库 + 恢复 + 核对 + 清理） |
| 迁移版本 | `flyway_max_version=3`，11 张业务表 |
| 行级一致性 | `app_user` 行内容 MD5 `e792ad9c75ac000a3b09390c52708180` 两侧一致（含本轮新设的口令哈希）；`flyway_schema_history` MD5 `9d20681a085c91560b6fd894094ad2b4` 两侧一致 |
| 留存策略 | 用 48 份合成备份验证：保留 20 份（日 7 + 周 4 + 月 12 的并集），最早一份落在 12 个月前，符合预期 |
| 定时任务 | `0 2 * * *` 已装；用 `env -i` 模拟 cron 的空环境试跑通过，不依赖交互式 PATH |
| 服务未受影响 | 演练期间 api 始终 healthy，生产库未被触碰 |

## 四、只在真机出现的四个坑

| 坑 | 现象 | 处理 |
|---|---|---|
| `.env.prod` 的 `GALLEY_RECONCILE_CRON=0 30 2 * * *` 未加引号 | `source` 该文件时把 `0 30 2 * * *` 当命令执行，报 `30: command not found`，其后的变量全部未赋值 | 值加双引号；脚本改为按键取值，不整体 source |
| 后四行由 Windows 经 scp 追加，带 CRLF | 值尾多一个 `\r`：`ossutil` 报 `invalid oss path`；shell 里拼出的桶名带不可见字符。compose 能容忍，shell 不能 | 全文件 `sed -i 's/\r$//'`；脚本取值时统一 `tr -d '\r'` |
| 首次装 crontab 失败 | `set -e` 下 `crontab -l` 在「尚无 crontab」时返回非 0，子 shell 提前退出，装上的是空表 | 改用 `{ crontab -l 2>/dev/null \|\| true; echo "$CRON"; } > 文件` 再 `crontab 文件` |
| `ossutil stat` 输出用 ` : ` 分隔 | 首版按 `Content-Length=` 解析，取到空值，等于校验没生效 | 改正则；空值直接判失败，避免“看起来通过” |

前两条属于部署配置形态问题，与 `1b37829` 修的三个编排缺陷同源：**CI 不解析 compose、也不解析 `.env` 的 shell 语义**，只有真机能暴露。

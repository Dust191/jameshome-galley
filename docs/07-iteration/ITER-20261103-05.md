## 三、变更过程

### 3.1 故障定位

13 个 Dependabot PR 的 CI 全红。确认主分支推送本身是绿的（`ci #1`，提交 `6e5b020`）后，
逐项排除：失败的是 `guards` job 的署名校验，失败范围里出现两类提交——

```
[FAIL] 7ba562 缺少 Signed-off-by: Merge 701b63b into 6e5b020
[FAIL] 701b63b Signed-off-by 与作者不一致  dependabot[bot] <support@github.com>
        vs dependabot[bot] <49699333+dependabot[bot]@users.noreply.github.com>
```

Dependabot 无法 rebase 时会退回 merge commit（7ba562），其提交树里有未经签署的机器人提交（701b63b）。
DCO 校验不区分人和机器、不区分内容提交与合并提交，于是**每一个 PR 都红**。

### 3.2 处置原则

署名检查的是「谁对内容负责」。机器人提交的内容最终由 Squash 合并的提交承载，责任落在合并者身上；
合并提交本身不承载内容。因此豁免是语义正确的，不是放水——人类贡献者的签署要求一个没松。

升级范围的约束用 `ignore` 而不是"看到再关"：Dependabot 会重建被关闭的 PR，
只有配置层面的 ignore 才能真正挡住。每条 ignore 都注明了解除条件（Maintainer 批准并更新配置）。

| 挡下的 | 理由 |
|---|---|
| antd ≥6、react ≥19、react-router ≥7、plugin-react ≥5 | UI 栈大版本联动（antd 5 与 react 19 的兼容性），属 0.2.0 级工程 |
| @tanstack/react-query ≥5.63 | 开发者裁定本轮关闭，先钉在 5.62；解除时评估跨度 |
| maven 发行版 ≥3.10 | 构建工具自身，单独开轮次 |
| actions 三件套 major | 与业务变更分开处理 |

| 教训 | ignore 清单只对照了"已出现过的 PR"，没有对照**依赖全量清单**推演哪些包会跨大版本。正确做法：写 ignore 时按 ecosystem 过一遍全部依赖，凡 major 不打算跟的都列上 |
## 九、补记二（2026-11-03 21:05）：tooling 组三连 major，ignore 再补三条

`#18`（tooling 组）的内容是 eslint 9→10、typescript 5.7→7.0、vite 6.4→8.3——三个大版本打包。
同日第二次补 ignore：`eslint ≥10`、`typescript ≥6`、`vite ≥7`，并关闭该 PR。

两轮下来的完整结论：**ignore 的写法应该是"凡 major 不跟的都列"，按依赖全量清单推演**，
而不是按"这周出现了什么"打补丁。 Monday 批次的处置结果见 §十（合并清单）。

## 三、变更过程

### 3.1 做法

豁免口径与署名校验严格一致（两条豁免的理由相同：合并提交不承载内容变更、机器人无法自守为它写的规则）：脚本从 `git log --format='%H%x09%P%x09%an%x09%s'` 一次取齐提交哈希、父提交、作者与标题，多父即合并提交、作者命中 `dependabot[bot]` / `github-actions[bot]` 即跳过；其余提交照旧检查格式、长度与句号。CI 步骤插在署名校验之前，范围同署名（`base..HEAD`）。

### 3.2 模拟评审（对抗式自查）

| 编号 | 发现 | 处置 |
|---|---|---|
| P-1 | 首稿把 `guards` job 的 `name` 改成「契约 + 环境变量 + 署名 + 提交信息」——该 name 是分支保护的**必需检查上下文**，改名会让所有 PR 卡在旧上下文上 | 保持原名不动，只在步骤层加一行，并加注释说明为什么不能改名 |
| P-2 | `git log --format` 一次取齐后，`%P` 在 rebase 遗留的空提交上可能为空串 | 空父串不含空格，走正常检查路径，行为正确 |
| P-3 | `wc -m` 在 Git Bash 的 UTF-8 locale 下按字符计数，中文 subject 长度正确（与既有 50 字规则一致，未引入新行为） | 保持原实现 |

### 3.3 验证手段与结果

| 项 | 结果 |
|---|---|
| 正例：`check-commit-message.sh origin/main`（全量历史） | 通过：检查 47 条人工提交，豁免机器人 12 条 |
| 负例：临时分支上制造不合规格式提交 | `rc=1`，输出「不合规」与期望格式（临时分支已删除） |
| `check-signoff.sh origin/main` | 通过（豁免口径未变） |
| `node scripts/check-docs.mjs` | 通过 |
| CI | PR 上三个 job 全绿后合并 |

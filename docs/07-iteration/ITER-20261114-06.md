## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净，无他人改动。
2. 方案 B 落成四步命令，重点在两头：构建时 tag 带日期与短哈希，避免与发布 tag 混淆；验证完必须把 `GALLEY_IMAGE_API` 改回发布 tag，否则 staging 与 prod 的「同镜像」前提就破了。
3. G5 对表时顺手查了生产库的数据量，得到物料 0 / 分类 0 / 流水 0 / 账号 1。这条直接推翻「数据组第 2 条已具备」的默认假设。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 生产库为空：系统虽在线上，但没有任何业务数据，只有 1 个管理员 | 写入 `DEV-009` §7.7「期初数据」一行，状态记「未导入」；G5 数据组第 2 条据此判为未达成 |
| P-2 | 定时任务只有备份一条 crontab；对账是应用内 `@Scheduled`，不体现在 crontab；清理任务（镜像、日志、旧备份）没有 | 运维组第 5 条判为「部分达成」，清理一项列为缺口 |
| P-3 | G5 标称「六组 30 项」，逐条数是 27 条 | 沿用既有记录，未擅自改为 27；盘点按实际 27 条计，此差异仍在待裁定 |

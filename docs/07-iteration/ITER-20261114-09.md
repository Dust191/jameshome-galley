## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净。
2. 迁移脚本用 `IF NOT EXISTS`：staging 已经手工建过同名索引，下次 Flyway 执行时应当跳过创建、只登记版本，不能因为「已存在」而失败。
3. 先在 staging 手工建索引验证效果，再决定是否值得发版；避免为一个未验证的方案走完整发布流程。
4. 复测按阶梯走：1 并发 → 4 并发，每步看停止原因。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 修改索引表时误把 `UNIQUE (reversal_of)` 那行覆盖掉了 | 立即回读文件发现，补回原行并核对整表 |
| P-2 | 4 并发 P95 1296ms，且 CPU 99% 只撑了 2 秒 | 判定为 CPU 瓶颈：`overview` 的 5 个 count 各自扫一遍 5 万物料，索引只解决了流水那一侧 |
| P-3 | 索引建在 staging 但 prod 没有；两边 schema 不同 | prod 是空库，影响为零；V4 会随下一版镜像上线，届时两边一致 |

### 3.3 验证手段与结果

| 项 | 结果 |
|---|---|
| 建索引 | 2 秒，26 MB |
| `overview` 单测（3 次） | 0.43 / 0.29 / 0.34 秒（原 3.10 / 3.00 秒） |
| 1 并发（15 秒） | 63 请求、0 错误、P50 285ms、**P95 386ms**、CPU 峰值 82.8% |
| 4 并发（20 秒上限） | 11 请求、0 错误、P50 1042ms、**P95 1296ms**、CPU 99.2%，2 秒即触停止点 |
| prod | 全程 200，未重启 |

## 六、与上轮的差异摘要

- 上轮定位到一条查询，本轮用 26 MB 的索引把它从 3 秒压到 0.3 秒。
- 单并发达标，4 并发暴露下一层瓶颈：CPU 而不是磁盘。
- 索引只治了流水那一侧，5 万物料的 5 次计数还没合并。

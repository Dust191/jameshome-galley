## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净，无他人改动。
2. **staging 用覆盖层，不复制一份编排。** 读 `compose.prod.yml` 后确认三件事：没有 `container_name`、端口全走 `expose` 不映射宿主、卷名为项目内相对名。因此隔离只需三样——项目名、宿主回环端口、数据卷（卷名随项目名前缀自动带上 `galley-staging_`）。复制整份文件反而会留下两份会各自漂移的配置。
3. `cloudflared` 用 `profiles: ["tunnel"]` 默认不启动：staging 走内网，不该占隧道，也不该产生一个对外地址。
4. 指标端点：只开 `metrics`，不开放 `prometheus`（未引依赖），并配 `http.server.requests` 的分位，否则该指标只有计数与总和，读不出 P95。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | `.gitignore` 的 `.env.*` 会把新模板一起忽略，模板进不了仓库，别人 clone 后无从复制 | 白名单加 `!infra/compose/.env.staging.example`，与 prod 模板同样处理 |
| P-2 | 本机没有 Docker，`compose config -q` 跑不了，覆盖层的变量插值与档位冲突无法本地验证 | 在 CI 的 guards 加一步「staging 编排校验」，用模板解析合并后的配置；本地只做 YAML 解析 |
| P-3 | staging 若沿用 prod 的 02:30 对账，两套任务会在同一分钟争 CPU 与磁盘 | staging 的 cron 改为 03:30；没有去关对账，因为关闭要透传 `galley.reconcile.scheduled`，会给 prod 编排引入新变量 |
| P-4 | `deploy.md` §2 明确「staging 与 prod 不共用 OSS bucket」，而现成的只有 prod 一个桶 | 模板里写 `jameshome-galley-staging`，桶未建前列为遗留；不为了省事让两套环境共桶 |
| P-5 | 指标端点开放后，安全边界靠什么保证 | 三层：Caddy 只转发 `/actuator/health*`、api 不映射公网端口、staging 的映射绑 `127.0.0.1`；SecurityConfig 的注释里写明这一点 |

## 六、与上轮的差异摘要

- 上两轮都在改口径，本轮第一次落实现：一份覆盖层、一份变量模板、一个端点。
- staging 用覆盖层而不是复制编排，理由是复制出来的两份配置迟早会漂。
- 指标端点只开 `metrics`，没有引 Prometheus，保持依赖表不变。

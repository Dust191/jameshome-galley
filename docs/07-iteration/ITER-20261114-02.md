## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净，无他人改动。
2. 五项裁定分两层落：判据层改 `DEV-009`（staging 落点、性能环境、发布窗口）；台账层改 `DEV-007` / `DEV-004`（分支保护第三项、OWASP 时机），并在 `DEV-008` 补一句评审边界。
3. 落点变化带来的连带修改：staging 从「同机或低配实例」改成本机内网虚拟机后，原「main 合并即自动部署」不再成立——CI 跑在公网，无法直连 `192.168.91.128`。触发改为手动，并把 D5-8、§7.7、T5-02 三处「staging 段待接」的说法一并改掉，否则会留下一条永远接不上的流水线段。
4. 环境差异项从「域名」改为「入口方式」：staging 在内网用 IP 直连，没有隧道也没有主机名，原表述对它不成立。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 只改三环境表，会留下三处「缺 staging 段」的旧说法，与新落点矛盾 | 同批改 D5-8、§7.7、T5-02，统一为「staging 由本地手动拉取，不在流水线内」 |
| P-2 | 性能改到 staging 后，`DVT-10` 的收回条件容易被误读成「staging 达标即可收回」 | 在 `DVT-10` 补记里写明：staging 是本地虚拟机，实测只证明代码路径与查询计划，不构成 2C1.7G 可承载的证明，偏离继续生效 |
| P-3 | `DVT-04` 的三项不开启此前只落了两项，`Prevent self-review` 一直没写进文档 | 按「只增不删可改」用补记追加，不改条目正文；同一补记里把三项的开启时机统一到 S6 |
| P-4 | 发布窗口与冻结期写在「单人期实践」里，读起来像约束 | 保留建议值，明写「只作参考，可违背」，避免后续把惯例当成违规 |

## 三、变更过程

### 3.1 执行步骤

1. M-1 ~ M-8 全部下沉为 SQL，Java 只做组装与比率换算——口径写在 SQL 里，核对时不必在两处跳。
2. M-5 的 30 个点用 `generate_series` 生成日期序列再左连流水，缺日由 SQL 补 0，不在 Java 里补。
3. M-9 直接复用结存的 `alert` 筛选，保证"预警数"与"预警清单"同源。
4. 比率统一 `HALF_UP` 保留 4 位，与文档"四舍五入"的字面对应。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 总览显示 `zeroStockCount=1`，但预警清单是空的 | 根因：`StockBalanceMapper` 以 `stock_balance` 为主表 `JOIN material`，从未入过库的物料**没有结存行**，于是从清单里消失。改为 `material LEFT JOIN stock_balance`，并把所有比较包上 `coalesce(..., 0)`。这与 M-2「无结存记录视为 0」的口径一致 |
| P-2 | M-2 与 M-3 会同时命中同一物料（结存 0、安全库存 20 时既算低库存也算零库存） | 按文档字面实现，不做互斥。M-9 已规定"同一物料命中多个条件取最高严重度、只出现一次"，去重发生在清单层而非计数层。此处登记供后续确认是否需要互斥 |

| 验证 | 结果 |

## 六、与上轮的差异摘要

上轮能记账但不能看账。本轮九项指标全部可用，且验证了最容易错的一条：
趋势图里 `OUT` 只算 1 笔，因为被红冲的那笔与原流水都不计入——这正是 DES-004 §4 要求的净口径。

实现时踩到的 P-1 值得记一笔：**统计口径写对了，查询的主表写错了，结果依然错**。
这类错误在单测里看不出来，只有把两个接口的结果摆在一起比对才会暴露。

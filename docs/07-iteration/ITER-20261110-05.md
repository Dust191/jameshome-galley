## 三、变更过程

### 3.1 关键设计

- **同一事务**：审计写在业务服务的 `@Transactional` 内，审计失败业务一起回滚；业务提交则审计必已写入，不存在"改了但没记"。
- **before 快照必须取在改动前**：更新类操作先 `snapshot(row)` 再改字段，否则前后一样。
- **jsonb 写入**：MyBatis 按字符串绑定 jsonb 会被 PG 拒绝，`AuditLogMapper` 显式 `#{...}::jsonb`。
- **账号快照脱敏**：`UserService.sanitizedUser` 只暴露账号名/显示名/角色/状态；重置口令只记"要求改密"这个事实，**临时口令与 password_hash 绝不入审计**（红线 5）。注册/登录/改密同样走该映射。
- **批量导入**：entityId 存批次 id（uuid v7），after 记 `{total, created, batch}`；行级追溯靠物料自己的 CREATE 审计与 `created_by`。

### 3.2 模拟评审（对抗式自查）

| 编号 | 发现 | 处置 |
|---|---|---|
| P-1 | 首稿把 `sanitizedUser(row)`（Map）直接当快照文本传给 `record`，类型不符 | 统一改为 `audit.snapshot(sanitizedUser(row))` |
| P-2 | Jackson 3 默认 pretty-print（`"reversed": false` 带空格），测试断言按无空格写法全部落空 | 断言按实际输出修正；审计文本入 jsonb，格式无关紧要 |
| P-3 | 测试里 WHERE 用了 SELECT 别名 `after_json`，PG 不允许 WHERE 引用别名 | WHERE 内改用 `after::text like ?` 传参 |
| P-4 | `AuditService` 若吞掉审计异常，会出现"业务成功、审计丢失"——违背收回条件 | 不捕获：审计异常随事务一起让业务失败（保守取舍，注释写明） |
| P-5 | 工作流 `guards` 的 job `name` 是必需检查上下文 | 本 PR 不触碰 CI |
| P-6 | 提交 subject 的 scope 取 `audit`，被新接入的提交信息校验拦截（白名单无此值）——新门禁第一次生效就咬住了本轮自己的提交 | scope 改取 `db`（审计落 `audit_log` 表）；不为此扩充白名单 |

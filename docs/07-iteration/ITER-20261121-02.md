## 三、变更过程

### 3.1 做法

先同步开发者批量审定的 13 份记录（`in_review` → `approved`，审定三行由其手填），再按 O-2 → O-3 → F-1 推进。

**O-2**：把六条业务规则写成 `alert-agent.py`。三条取舍：

- 不装 SDK。DirectMail 用 ACS3-HMAC-SHA256 手写签名，脚本只用标准库，2G 内存的机器上不引入依赖。
- B-4 不用 `/actuator/metrics`。0.2.2 上该端点只输出 COUNT / TOTAL_TIME / MAX，没有分位；改从 Caddy 访问日志的 `duration` 算 P95，B-3 的 5xx 比例同源。
- 只在状态变化时发信，持续故障每 6 小时提醒一次，恢复补一封；样本不足 20 记 `SKIP`，不判定。

**O-3**：`rollback.sh` 做六步——确认当前 tag、确保目标镜像在本地（缺则从 ACR 拉）、备份 `.env`、重建 api/web、轮询健康、冒烟。任一步失败即把 `.env` 退回原 tag 并重建，退出码 2。

**F-1**：写 `uat-staging.py`，在 staging 真数据上跑。能现场复现的 11 条直接打接口；第 11 条「空数据总览」在 staging 无法复现（5 万物料已造满），仍由 CI 用例出证。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 发信返回 `InvalidMailAddressStatus.Malformed`（签名已通过，是业务错误） | 判定为发信地址状态问题，需在 DirectMail 控制台核对；本轮不绕过，如实记未完成 |
| P-2 | B-5 误报「没有任何导出文件」 | 备份实际在 `backup/db/` 子目录，改为递归查找，复跑转 OK |
| P-3 | UAT-4 出库返回 400「出库数量必须为负数」 | 契约要求出库带负号，脚本改为 -150，结存 -50 符合预期 |
| P-4 | UAT-6 冲正返回 400「冲正原因不能为空」 | 补 `note` 字段；重复冲正仍按预期 422 |
| P-5 | UAT-12 导出返回 422 `EXPORT_TOO_LARGE` | staging 正好 5 万物料，触到 50000 行上限；改为按关键字导出，BOM 校验通过。该 422 是设计行为，不是缺陷 |
| P-6 | `rollback.sh` 在云上报 `bash\r` | Windows 侧写入带 CRLF，安装后 `sed -i 's/\r$//'` 更正；后续提交由 git 归一 |

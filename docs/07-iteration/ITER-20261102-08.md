## 三、变更过程

### 3.1 执行步骤

1. 先写 CSV 解析器并配 9 个用例——导入的所有诡异表现最终都归到"某一列错位"，先把这层钉死。
2. 导入策略定为 **全量校验 → 全部通过才写库**：任何一行有问题就整体不写，返回全部错误行。
3. 分类与单位按名称精确匹配、**不自动创建**：拼错一个分类名就静默造出新分类，比报错更难发现。
4. 导入接口有错误行也返回 200：请求成功、数据有问题，用 4xx 会让前端把"几行填错"当成"接口调不通"。
5. 补上契约里写了但未实现的 `GET /exports/movements.csv`。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 导入若"逐行提交"，用户改完重导会撞唯一键，还得人工比对哪些已写入 | 改为整批事务：有错就一条不写，用户改完直接重导 |
| P-2 | Excel 另存的 CSV 带 BOM，不去掉会让第一列表头变成 `﻿自编码` | 解析器首字符判断并剥掉 |
| P-3 | 规格字段常写 `25kg/袋, 加厚`，按逗号硬切会错列 | 按 RFC 4180 处理引号：引号内的逗号与换行都不切 |
| P-4 | `MaterialExportService` 原本只导出物料，加流水后耦合两个 Mapper | 保留一个服务、两个方法，共用 `withBom` 与 `appendRow`；拆成两个服务反而要复制转义逻辑 |

### 3.3 验证手段与结果

用一份**故意混入 3 行错误**的 CSV 实测：

| 场景 | 结果 |
|---|---|
| 5 行含 3 行错误 | `{"total":5,"created":0,"errors":[...]}`，行号 4/5/6 与 Excel 行号一致 |
| 错误字段 | 「物料名不能为空」「「不存在的分类」不存在」「安全库存不能为负数」分别命中 |
| 正确导入 2 行 | `{"total":2,"created":2,"errors":[]}`，物料总数由 2 增至 4 |
| 引号内逗号 | 规格 `25kg/袋, 加厚` 完整保留，未错列 |
| 重复导入同一文件 | 409 `DUPLICATE_KEY`，整批回滚，未产生半截数据 |
| 流水导出 | 200，496 字节，前 3 字节 `ef bb bf`；6 条流水按时间倒序，被红冲的标"是" |
| 流水导出时间 | `2026-11-02 13:12:30`（上海时区），非 UTC |
| `mvn test` | 55 个用例通过（新增 9 个） |

## 八、补记（2026-11-03 15:20）

| 编号 | 补记前 | 补记后 |
|---|---|---|
| L-01 | 未决：导入不做更新语义 | **已关闭**：开发者 2026-11-02 复核时明确认可「自编码已存在直接报冲突、不覆盖」，理由是一次误传不应改写既有物料的规格与安全库存 |
| L-02 | 未决：分类/单位不自动创建 | **已关闭**：同上，开发者认可「拼错即报错」，避免错别字静默变成新分类 |
| L-03 | 未决：整批原子、超大文件失败需全量重导 | **维持整批原子**：逐行事务会把"半截写入"重新引回（正是 P-1 要避免的），失败重导的代价小于数据不一致。不记为技术债 |

补充说明：本轮只做了后端接口与 CSV 解析测试；导入的界面入口在 `ITER-20261103-03` 补齐
（`MaterialImportModal`），用于 G3 的 E2E 走通「上传 → 逐行错误」这条链路，接口与校验语义未改。

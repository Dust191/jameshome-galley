## 三、变更过程

### 3.1 做法

1. 开局 `git status --short` 与 `git diff`：工作区干净，无他人改动。
2. 造数不走接口走 `\copy`：200 万条走 API 不是一个晚上的事。期初结存做成基准日每个物料一条 `ADJUST`，结存由 `sum(quantity)` 聚合——这样「结存由流水推出」这条红线在造数路径上也没破。
3. 压测只发 GET，不写数据；停止点不靠「跑满 N 秒」，而靠每 2 秒采一次整机 CPU / 内存 / 磁盘，任一达到「告警阈值 − 5」就置停止标志。
4. 在 ECS 上用 1000 物料 / 2 万流水验证整条链路，确认脚本可用后再交付。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 首次登录拿不到会话 cookie：代码写死找 `SESSION`，实际下发的是 `JSESSIONID` | 改为「取登录后新增且不是 XSRF 的那个 cookie」，不写死名字；同时记下 `DES-002` 与实现不一致 |
| P-2 | 导入后直接压测，CPU 首次采样就到 99%，P95 抖动 | 根因之一是没跑 `ANALYZE`，统计信息为空导致全表扫；已把 `ANALYZE` 写进导入步骤 |
| P-3 | staging 用 `debug` 日志，每条 SQL 与参数都刷进 json-file，IO 开销进了压测结果 | 压测前切 `info` 并重启 api；文档写明这是压测前置条件 |
| P-4 | api 刚重启时 JIT 编译集中在前几十次请求，首轮 CPU 打满、P99 到 646ms | 脚本加预热（默认 20 次，不计入统计）；重启后先预热再采样 |
| P-5 | 每次重启 api 都会重新生成管理员口令，用旧口令登录返回 401 | 文档里的压测命令改为从当次日志取口令；`cut -d：` 因中文冒号是多字节不可用，改 `sed` |
| P-6 | 2 秒采样下，4 个并发的总览查询就能把 2 vCPU 打满 | 这是真实结论而非脚本缺陷：总览是重聚合查询。已记入下文实测观察 |

### 3.3 验证手段与结果

| 项 | 结果 |
|---|---|
| 造数（1000 物料 / 2 万流水） | 生成 4 个 TSV 共 4.4 MB；`\copy` 全部成功：8 分类 / 6 单位 / 1000 物料 / 20000 流水 |
| 结存聚合 | 1000 条结存，负结存 1 条（随机出库导致，符合允许负结存的规则） |
| 压测（2 并发 / 10 秒） | 39 请求、0 错误、P50 105ms、P95 138ms |
| 压测（4 并发 / 20 秒） | 77 请求、0 错误、P50 106ms、P95 145ms、RPS 38 |
| 停止点判定 | 正确触发：`stopped_because` 记「CPU 达到 100.0%，触及停止点 80%」 |
| 数据清理 | 验证后 `TRUNCATE` 四张表，staging 回到空库，等全量造数 |

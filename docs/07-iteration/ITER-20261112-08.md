## 三、落地时发现的第三个问题

写模板时守卫报「`.env.prod.example` 定义但编排未使用」，牵出实际缺陷：

```
compose.prod.yml 里 GALLEY_ENV: prod          ← 写死
                  GALLEY_LOG_LEVEL: info      ← 写死
                  GALLEY_RECONCILE_CRON       ← 压根没传给容器
```

含义是：**运维在 `.env.prod` 里改这三项完全不生效**。`GALLEY_RECONCILE_CRON` 尤其隐蔽——对账任务会一直按 `application.yml` 的默认值 `0 30 2 * * *` 跑，`DVT-11` 里“自建库靠日备份兜底”的说法也因此少了调整手段。

三项均改为 `${VAR:-默认值}` 透传，YAML 里 cron 值加引号（含 `*`）。用模板跑 `config` 复核，三个值都能正确解析。

## 五、为什么值得改 CI

三个 compose 缺陷与两个 `.env` 缺陷有一个共同点：**CI 从来不看这两类文件**。`check-env-example.sh` 只比对键名，不解析编排；compose 的插值语法只有 `config` 会验；`.env` 在 shell 下的语义只有真 `source` 一次才暴露。

这次把能自动化的两条（编排解析、格式规则）放进了 `guards`，剩下“shell 语义”一条由脚本按键取值来规避——备份脚本已改成不整体 `source`。

## 四、两个设计取舍（需开发者确认）

**1. 管理员密码策略分环境**。开发环境**每次启动**重新生成 16 位随机密码并打印到启动日志（实测 `WfKtTWdBAgN8fXZL`），重启即换、以本次日志为准；生产环境（`GALLEY_ENV=prod`）只在账号不存在时创建一次并强制首登改密，已存在则不触碰。固定密码的环境变量（`GALLEY_BOOTSTRAP_ADMIN_PASSWORD`）已删除——那正是弱口令后门的入口。

**2. 冲正记录的类型口径**。"冲正"在界面上是一种独立类型（灰色 Tag），不算入库也不算出库；趋势图注释中已写明。若业务上希望冲正在明细里显示为"+80（冲销原出库）"这类合并形态，需要再改展示层。

## 八、补记（2026-11-02 20:30）：返工引入的阻断级缺陷

开发者实测发现：`QtyInput.handleBlur` 只在 `clampQty` 返回改写值时才调 `onChange`——
输入 5、10 这类本来合法的数时 `clampQty` 返回 `value: null`，`onChange` 从未被调用，
**表单里根本没有值**。后果：安全库存填 5 保存后显示 0.000（存了初始值 0）；
流水数量填 10 提交时红字报"请输入数量"。返工后没有任何一笔新流水能通过正常输入提交，
现有流水全部是返工前所建。

| 项 | 说明 |
|---|---|
| 根因 | 受控逻辑写反：把 `onChange` 挂在"值被修正"这个分支上，而合法值恰恰走 `value: null` 分支 |
| 连带缺陷 | `onChange` 只挂失焦，与点击提交存在时序竞态——即便补上失焦同步，Form 的 `onFinish` 仍可能读到旧值 |
| 修复 | 改为**输入即同步**：文本能解析为数字立刻 `onChange`（解析不了的中间态如单独的 `-` 暂不传，等继续输入）；失焦只做两件事——归一化三位小数展示、被改写时红字说明。另加 `editingRef` 防止输入中的中间态（`"5."`）被外部回流值覆盖成 `"5"` |
| 修复后验证 | typecheck / lint / build 全部通过；修复逻辑走查：填 5 → 表单值 5；填 10 出库 → 提交 -10；填 -3 失焦 → 归零 + 红字；填 1.23456 失焦 → 1.235 + 红字 |
| 教训 | "提示组件"与"受控组件"两个职责混在一个 `handleBlur` 里，受控的职责被提示的分支吃掉了。本该一入参数据流（输入即同步）+ 一条展示流（失焦提示），而不是让后者门控前者 |

> 本次缺陷由开发者实测发现，模型此前以"构建通过"替代了输入链路验证——这是第二次在同一处跌倒
> （第一次是不连库导致迁移不执行）。已记入教训：表单类改动必须人工走查一条完整输入路径，
> 不能以静态检查代替。

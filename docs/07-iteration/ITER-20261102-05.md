## 三、变更过程

### 3.1 执行步骤

1. 先定幂等方案：加 `idempotency_key` 列 + 部分唯一索引，而不是另建幂等表——幂等只是流水的一个属性，独立成表会让"哪条流水对应哪次请求"多一层间接。
2. 结存更新写成一条 `INSERT ... ON CONFLICT DO UPDATE SET quantity = quantity + EXCLUDED.quantity`，不做"读—算—写"。
3. 红冲用 `UPDATE ... SET reversed = true WHERE id = ? AND reversed = false` 的结果作并发闸门：影响行数为 0 说明别人刚冲过。
4. 严重度表达式放进 SQL 而不是 Java：分页后再算会导致跨页顺序错乱。
5. 按 DES-004 M-9 的边界逐条写测试：负、零、低于安全线（严格小于）、安全库存为 0 视为不设线。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 登记与红冲的返回体里 `materialName`、`unitName`、`operatorName` 都是 null | 因为走的是无 join 的 DO 转换。补 `findRowById`，创建/红冲后回查一次带 join 的视图 |
| P-2 | 「红冲的红冲」在文档里没写清该怎么处理 | 按"红冲不是业务动作"处理：直接拒绝并返回 400。若要撤销红冲，应重新登记一条正常流水 |

### 3.3 验证手段与结果

在真实 PostgreSQL 18.3 上按记账全链路逐项实测：

| 验证 | 结果 |
|---|---|
| V3 迁移 | `Successfully applied 1 migration`，now at v3 |
| 入库 100 | 201，结存 100，严重度 0 |
| 出库 -30 | 201，结存 70 |
| 出库 -80（超结存） | 201，结存 **-10**，严重度 **3**（UAT-4：允许负结存并按最高严重度预警） |
| 红冲 -80 | 201，生成 `REVERSAL +80`，结存回到 70 |
| 重复红冲 | 422 `MOVEMENT_ALREADY_REVERSED` |
| 幂等键重复提交 | 两次返回**同一 id**，结存只 +5（75 而非 80） |
| 入库传负数 / 出库传正数 | 400 `VALIDATION_FAILED`，`field=quantity` |
| 手工登记 `REVERSAL` | 400 —— 红冲只能走专用接口 |
| 挂 5 条流水的物料软删 | 422 `MATERIAL_HAS_MOVEMENTS`，回报流水条数 |
| 结存恒等式 | 结存 **77** = 流水求和 **77**（100−30−80+80+5+2，含被红冲与红冲本身） |
| `mvn test` | 46 个用例通过 |

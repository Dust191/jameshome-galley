## 三、变更过程

### 3.1 执行步骤

1. 先 `git diff` / `git status` 确认无手改，再读 GOV-000 §4 全文，提取 19 份强制文档、G2 九项、§4.4 写作规则。
2. 产出 S2 任务清单（8 项任务，见第五节），按"先立尺子再量东西"排序：模板 → 校验 → 设计 → 规范 → 运维治理 → 收口。
3. 写 5 份模板，把 §4.4.4 的写作规则以注释形式嵌在模板里，避免写着写着忘掉。
4. 写 `check-docs.mjs`，先以 `--warn-only` 试跑，摸清误报来源。
5. 写 DES-001，把"`reversed` 不参与求和"这类隐含规则显式化，并把 3 个需要决策的点单列成 §6。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 禁用写法反查首次运行 13 个文件全部告警，词为"迭代""评审""验收""用户"等泛用词 | 判为 **glossary 词条缺陷**而非文档缺陷：`迭代记录`、`用户故事`、`阶段门验收` 是既有固定说法，却被列进禁用写法。按 G-6 属全局口径变更，须走 RFC，本轮不擅改；校验先按"告警不阻断"处理，见遗留 L-01 |
| P-2 | 邀请码是否独立成表此前一直悬着（ITER-20261031-01 记「由 DES-001 定」） | 这是 H1 决策类，不自行拍板。DES-001 §6 给出 A/B/C 三选项与建议，等开发者裁定 |

## 三、变更过程

### 3.1 做法

1. 推送前先跑全量校验：`check-commit-message.sh origin/main..HEAD` 与 `check-signoff.sh`，8 条全过，再 `git push`。
2. 上机先看底数：内存 1740 MB（用 870 / 可用 870）、磁盘 40 GB（用 6.8 / 剩 31）、prod 五服务已连跑 39 小时。
3. 传两份编排文件；从 `.env.prod` 取 AK/SK，生成 24 位库口令，写出 `.env.staging` 并置 600。库口令与 prod 不同，桶指向 `jameshome-galley-staging`（先 `ossutil ls` 确认桶可达，0 个对象，AK 有 `List` 权限）。
4. 在真机上跑 `compose config -q`——这是覆盖层第一次与基础编排合并解析。
5. 分三步启动：`db` → `api` → `web` `caddy`，每步之间看一次内存。一次性全起会让启动峰值叠在一起，分不清是谁吃掉的。
6. 冒烟：健康（经 caddy 与直连 api 各一次）、首页 200、CSRF 200、登录 200、`/auth/me` 200。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | `/actuator/metrics` 返回 **401**：staging 用的是发布镜像 `0.2.0`，而开指标的代码是 11-14 才提交的，镜像里没有 | 不擅自改镜像 tag（「同镜像同编排」是判据）。本轮只完成代码侧，生效要等下一版镜像；`RUN-003` §6 如实记为「代码已加，镜像未含」 |
| P-2 | 本机没有 Docker，覆盖层此前只做过 YAML 解析，没做过真正的合并校验 | CI 的「staging 编排校验」先验了一次；上机后又用真机 `config -q` 验了第二次，两次都过 |
| P-3 | staging 用 `debug` 日志，SQL 参数把密码哈希打进了日志 | staging 可接受；prod 仍是 `info`。已记入遗留：任何情况下不要把 debug 带到 prod |
| P-4 | 同机内存：两套静态占用合计约 730 MB，剩余约 590 MB | 三步启动摸清了各步增量（db +6、api +239、web+caddy +27）。压测时 PG 与 JVM 都会涨，必须按 `DEV-009` §7.6 的停止点执行 |

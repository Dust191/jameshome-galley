## 三、变更过程

### 3.1 做法

先把「谁负责把镜像送进 ACR」定下来。三条路都试过：

1. **本机虚拟机中转**（原设想）：虚拟机 dockerd 的代理指向 7891 隧道，隧道起来后 `curl` 能通（401，1.06 秒），但 `docker pull` 连续三次在取 manifest 时 `EOF` 或 TLS 握手超时——代理对 registry API 不稳。虚拟机无免密 sudo，改不了 dockerd 的 `NO_PROXY`，此路放弃。
2. **ECS 直连 GHCR**：可行但慢，0.2.1 拉了 3 分 57 秒，0.2.2 两次都在 10 分钟上限附近被截断，正是开发者要求避免的路径。
3. **流水线同步**：`release.yml` 增加 `acr-sync`，构建完成后把同一份镜像推进 ACR。ECS 只认 ACR 的 `-vpc` 域名。选定这条。

同步方式试了四轮：

| 轮 | 做法 | 结果 |
|---|---|---|
| 1 | `buildx imagetools create` | 镜像名含大写 `Dust191`，直接报格式错误 |
| 2 | 小写归一后再 `imagetools create` | 403 `unknown manifest class for application/vnd.oci.empty.v1+json` |
| 3 | `pull` + `tag` + `push` | 仍 403，整个索引连同 attestation 一起被推 |
| 4 | 读出 amd64 单平台清单的 digest，按 digest 拉、再 tag、再 push | 成功，两个 job 均绿 |

第 4 步之所以成立：ACR 个人版拒收 config 为 `oci.empty` 的工件，而按单平台清单 digest 拉下来的镜像不含索引，推送时是普通 manifest。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 上一轮被中断的 `docker pull ghcr...0.2.2` 与 `compose up --wait` 在 ECS 上残留近 40 分钟，挡住宿主拉取 | 按命令行特征 kill 掉四个进程，再重试；以后长任务一律后台跑并记录 pid |
| P-2 | `-vpc` 域名被 Docker 视为另一个注册表，`pull access denied` | 把公网域名的 auth 记录复制一份给 `-vpc` 域名，两条并存 |
| P-3 | 同步后的首次 `compose pull` 失败，报 web 仓库不存在 | 同 P-2，登录记录补齐后一次成功 |
| P-4 | 文档里写部署账号家目录的绝对路径时触发词表禁用写法 | 改为「部署账号的 `~/.docker/config.json`」，语义不变 |

## 三、变更过程

### 3.1 做法

1. 先摸底：两条任务均为登录触发（延迟 15 秒）、当前正在运行。停任务 → 改 `install-tunnels.ps1`（去掉 `-Trigger`，注册后不再自启，结尾提示改用 start/stop 脚本）→ 重新注册 → 手动启动恢复隧道。
2. 模板与规范改写：全仓搜「回答」，确认除迭代记录外，其余都是各文档自己的定位语与 §2.5 通用规则；词表「迭代记录」定义与执行记录定位不冲突，不动。§2.5 保持通用规则不改，迭代记录的定位要求写进 §2.7。

### 3.2 遇到的问题与处理

| 编号 | 问题 | 处理 |
|---|---|---|
| P-1 | 云端隧道重启回连时报 `remote port forwarding failed for listen port 7892`：本地杀掉旧连接后，云端残留 `sshd` 会话仍占着 7892 | 到云上 `ss -tlnp` 定位占用端口的残留 `sshd`（pid 220942）并结束；下一次重连即成功，7892 监听恢复 |
| P-2 | 虚拟机 `192.168.91.128` 当前 ping 不通（未开机） | 隧道任务每 10 秒重试一次，虚拟机上线后自动恢复，无需人工 |
| P-3 | 启停脚本里 `timeout /t` 在 Git Bash 环境被 coreutils 的同名命令抢先，报 `invalid time interval` | 脚本改用 `powershell Start-Sleep` 计时，内容保持纯 ASCII，规避编码与 PATH 两类坑 |

## 八、补记

**补记（2026-11-13 上午，开发者反馈「停止后仍有终端残留」）**：查明根因——`Stop-ScheduledTask` 只杀任务主进程（runner `powershell.exe`），由它启动的 `ssh.exe` 及其终端宿主 `conhost.exe` 不随之退出，成为孤儿进程（实测 cloud 侧孤儿 `ssh` pid 10520 一直活着，云端 7892 转发其实仍在工作；孤儿 `conhost` pid 39000 即任务管理器「终端」分组里看到的残留）。处置：启停操作整合为统一入口 `tunnels.ps1`（`status` / `start` / `stop` / `install` / `uninstall`，支持 `-Target all|cloud|vm`），`stop` 增加按命令行特征（`tunnel-runner.ps1`、`-R 789[12]:`）清扫孤儿的步骤；五个 `.cmd` 保留为薄封装（双击入口），退役的 `install-tunnels.ps1` 已送回收站。实测 stop 清扫后云端 7892 监听即消失，隧道真正全停。

# DEV-010 团体开发规范

这份文档回答一个问题：**上线之后，即使仍然只有一个人，怎么按"换个人也能接手"的标准分工、评审、值班与交接。**

当前状态：**未生效**。生效条件是 G5 通过（系统上线且稳定运行）。在此之前，仓库按 `DEV-008` 的作业规范执行；本文件先行定稿，是为了让 S5 的收尾有明确目标，而不是上线后临时补规矩。

## 1. 生效条件：上线即进入，与人数无关

G5 通过即进入团体开发规范期。判断标准不是"有没有第二个人"，而是"**换一个人来，能不能在不问原作者的前提下完成一次发布**"。

| 步骤 | 产出 | 完成判据 |
|---|---|---|
| 设计 | `GOVERNANCE` 更新：角色、决策路径、评审要求、值班安排 | 每条规则写明"谁做、何时做、做到什么程度" |
| 制定 | `DEV-002`、`GOV-002`、`CONTRIBUTING` 定稿并公示 | 文件之间交叉引用，无冲突表述 |
| 遵循 | 连续两个轮次按规范执行，迭代记录留痕 | 无"这次特殊，先跳过"的记录 |

单人最容易跳过"制定"直接"遵循"自己的习惯，这正是本阶段要避免的：**规范的价值在于可传递，而不在于正确**。

## 2. 必须建立并遵循的十二项规范

| # | 规范 | 单人期如何落地 | 当前状态 |
|---|---|---|---|
| 1 | 分支模型与保护 | S1 已建立，S4 补验 | 已生效；`enforce_admins: false`（`DVT-04`） |

## 3. 单人如何真正执行"团队规范"

最大敌人是自我豁免：规则写给未来的队友，自己照样绕过。四条机制对抗它：

| 机制 | 做法 | 作用 |
|---|---|---|
| 角色分离 | 同一变更的作者与批准之间至少间隔 12 小时再合并 | 让第二天的自己审第一天的自己 |
| 自审清单 | PR 描述逐条勾选十项 | 把"凭感觉"变成"逐项确认" |
| 自动化替代人工 | CI、ArchUnit、契约校验、依赖扫描、用词反查全部前置 | 机器能查的不靠自觉 |
| 外部视角 | 每轮请他人或模型做对抗式审查，问题写入迭代记录 | 发现问题，但不构成批准（H4） |

自审十项：① 边界（空值、超长、并发）；② 错误码复用既有常量；③ 新增查询有索引支撑；④ 写操作写审计；⑤ 补了对应测试；⑥ 更新受影响文档；⑦ 新词已登记；⑧ 迁移前滚兼容；⑨ 日志含 `traceId` 且不含敏感信息；⑩ 能在 5 分钟内回滚。

## 4. 扩编后的分工

实际协作人数 ≥2 时按下表分工。**按领域纵切，不按前后端横切**——本项目前后端比例接近 1:1，横切会让每个功能都跨组排期。

### 4.1 三到五人

| 角色 | 职责范围 | 兼任 |
|---|---|---|
| 物料域 Owner | `material`、`material_category`、`unit`、导入导出，后端 + 前端全栈 | 兼库存域评审 |
| 库存域 Owner | `stock`：流水、结存、红冲、盘点 | 兼物料域评审 |
| 统计域 Owner | 指标口径、聚合查询、总览页、报表 | 兼平台域评审 |
| 平台域 Owner | 认证授权、数据库、CI/CD、云上运维、监控 | 兼安全响应 |
| 体验 Owner（可选） | 设计系统、移动端只读视图、无障碍 | 兼文档维护 |

原则：每人是一个域的所有者 + 另一个域的评审者，保证任何改动至少有两人理解。

### 4.2 六到十人

在 3–5 人基础上拆两条 stream：

| Stream | 包含 | 交付节律 |
|---|---|---|
| Product Stream | 物料域、库存域、统计域、体验 | 跟随轮次 |
| Platform Stream | 认证、数据、运行环境、可观测性 | 独立小步，随需发布 |

新增角色可兼职：QA（维护 UAT 与回归集）、文档维护者（保证文档与词条不过期）、发布经理（轮值）。

### 4.3 扩编触发信号（满足任意两条）

| 信号 | 阈值 |
|---|---|
| Backlog 积压 | 未处理 issue >15 或平均首响 >72 小时 |
| 稳定外部贡献 | 连续 4 周每周 ≥1 个外部 PR |
| 并行需求 | 同时有 ≥2 个互不依赖的特性需要推进 |
| 单点风险 | 只有一人能执行发布或恢复 |
| 使用方增加 | 服务 ≥3 个厨房或 ≥200 名用户 |

## 5. RACI 矩阵

| 事项 | Owner | 物料域 | 库存域 | 统计域 | 平台域 | 社区 |
|---|---|---|---|---|---|---|
| 范围与优先级 | A | C | C | C | C | I |
| 领域模型变更 | A | R | R | C | C | I |
| 指标口径定义 | I | C | C | **A/R** | C | I |
| 接口契约 | I | R | R | R | C | I |
| 数据库迁移 | I | C | C | C | **A/R** | I |
| 结存对账与差异处置 | I | C | **A/R** | C | C | I |
| 发布执行 | A | I | I | I | **R** | I |
| 安全响应 | A | C | C | C | **R** | I |
| 贡献者分流 | I | C | C | C | C | **A/R** |
| 文档与词条 | A | R | R | R | R | I |

R = 执行，A = 最终负责，C = 需咨询，I = 需告知。每行有且仅有一个 A。

## 6. CODEOWNERS 映射

单人期全部指向 `@Dust191`，但文件按域书写，扩编时只改 handle、不改结构：

```

/backend/src/main/resources/db/migration/    @Dust191
/infra/                                      @Dust191
```

## 7. 协作机制

| 机制 | 规则 |
|---|---|
| 代码评审 | 1 人批准即可合并；`db/migration/`、`infra/`、`identity/` 需 2 人 |
| 评审时效 | 24 小时内首轮响应；48 小时未响应可升级至 Owner |
| 冷静期 | 单人期作者与批准间隔 ≥12 小时；多人期不强制 |
| 结对 | 高风险变更（迁移、认证、结存逻辑、指标口径）建议结对走查 |
| 设计评审 | 涉及表结构、接口契约、指标口径的变更，先 RFC 后编码 |
| 值班 | 每周轮值 1 人，负责告警响应与 issue 分流；值班期不安排大功能 |
| 同步会 | 每周一次 30 分钟架构同步，只讨论跨域问题；其余异步 |
| 决策 | Lazy consensus 72 小时；僵持则 RFC + 维护者投票，Owner 裁决并写 ADR |

## 8. 交接与离线演练

### 8.1 新人四周交接

| 周 | 目标 | 动作 | 验收 |
|---|---|---|---|
| W1 | 建立共同心智 | 架构走查两次（数据模型 / 请求链路）、代码导览、文档与词条通读、认领一个域 | 能独立解释一次完整写请求的路径 |
| W2 | 影子操作 | 新人执行发布、处理 3 个 issue，老人旁观不干预 | 发布成功，回滚脚本被执行过一次 |
| W3 | 独立操作 | 新人独立完成一次完整发布（备份、发布、验证）、独立分流一周 issue | 发布检查单由新人签字 |
| W4 | 责任转移 | CODEOWNERS 切为多人、值班表启动、回顾会由新人主持 | 老人休假 3 天系统无阻塞 |

### 8.2 单人期离线演练（每季度一次）

即使没有新人，也要模拟"原作者不在"：按 `RUN-001` 从零部署一次、恢复一次备份、发布一个补丁，全程只读文档不查记忆，记录写入 `RUN-002`。**这是检验规范是否真的可传递的唯一手段。**

首次演练的前置是 S5 完成：没有生产环境、没有备份、没有发布流水线时，演练只能验证文档，不能验证恢复。

## 9. 关键约束

1. 任何目录不得只有一个人有合并权限；`LICENSE`、`GOVERNANCE.md`、`00-glossary.md` 由 Owner 独占是唯一例外。
2. 值班期间不得进行数据库迁移与破坏性变更。
3. 跨域变更必须由两个域的 Owner 共同批准，不得单方推进。
4. 禁止"先合并再补文档"；文档影响项为空的 PR 须说明理由。
5. 新成员第一个 PR 必须是文档或测试类改动，用于熟悉流程而非产出功能。
6. **单人期不得以"就我一个人"为由跳过评审、迭代记录或发布检查单。**

### 2.4 规范标准

**范围冻结表三列**：In 写"构成最小闭环"的功能，Out 写"与定位无因果关系"的功能并给理由，参考方向写"已识别、未审定、不实现"的方向。

**用户故事写法**：

```
作为 <角色>，我希望 <能力>，以便 <价值>。
验收：给定 <前置>，当 <操作>，则 <可观测结果>。
```

每条故事至少两条可断言验收条件（有具体数值、状态码或界面元素）。

**非功能基线六项**：

| 维度 | 指标 | 口径 |
|---|---|---|
| 性能 | 总览 P95 ≤500ms；列表 P95 ≤300ms | 5 万物料、200 万流水、并发 20 |
| 容量 | 5 万物料、200 万流水、50 账号、日活 50 | 超过则触发架构评审 |
| 可用性 | 月度 ≥99%（允许计划内维护 2 小时） | 单机部署的现实目标 |
| 安全 | OWASP Top 10 自查通过；依赖无 High/Critical | 每次发版前 |
| 兼容 | Chrome / Edge / Safari 最近两个大版本；移动端浏览器只读可用 | 远程查看常发生在手机上 |
| 无障碍 | 表单可键盘操作、对比度 ≥4.5:1 | WCAG 2.1 AA 关键项 |

### 2.5 关键约束

1. 范围表过 G0 后，新增需求只能进参考方向或下个 minor，不得插入当前 MVP；例外仅限数据错误类缺陷。
2. PRD 不出现"等""类似""视情况"等模糊词；每个功能对应一条可执行验收。
3. 定位只在本阶段讨论一次并冻结，后续不重开。
4. 不写代码、不建仓库，先出文档；文档未定稿不开工。

### 3.4 规范标准

命名、分层、提交、分支的完整规则见 `DEV-008` §3 ~ §4；本阶段只强调四条骨架期纪律：

- **模块边界先立**：`modules/{material,stock,stats,identity}` + `common/{error,audit,config,security}` 的划分在写第一行业务代码前定下，后续只增不改骨架。
- **CI 必须随首次提交存在**，不得"等有代码了再加"。
- **`.env` 永不入库**，`.env.example` 与 `application.yml` 的变量一一对应，`check-env-example.sh` 校验。
- **JDK 两级锁定**：大版本 25 由 CI 与本机对齐；补丁号由本机环境决定，CI 允许同大版本最新补丁，实际版本记入迭代记录。

### 3.5 关键约束

1. 骨架阶段零业务代码，只允许 `healthz` 与 ArchUnit 测试。
2. `make` 是唯一命令入口；长命令只存在于 Makefile 内部。
3. 容器操作在本机不可用时，用 `make sync` 同步到虚拟机执行，不在文档里散落 SSH 命令。
4. 单人期也走 PR：自己开、自己批，但必须留下 PR 记录（建仓前为本地模拟流程）。
5. 提交必须带 `Refs` 与 `Signed-off-by`；`Assisted-by` 选填但填写即受真实性约束。

4. 禁用写法零容忍；易混提示只告警。
5. 迭代记录只增不改；错误用"补记"追加。
6. 禁止用图片承载关键信息（截图里的表格、图片里的流程）。

| 数据库 | 只前滚，不回滚；expand-contract | — |
| 数据损坏 | PITR 或 `pg_dump` 恢复 | ≤2 小时 |

**迁移纪律**：expand（加列/表，新旧代码都能跑）→ migrate（双写或回填）→ contract（确认无旧代码依赖后，下个版本删旧列）。禁止同一版本内"加列 + 强依赖 + 删旧列"。

**可观测性**：

| 类别 | 要求 |
|---|---|
| 日志 | JSON；含 `timestamp`、`level`、`traceId`、`route`、`status`、`durationMs`、`userId`（脱敏）；不记录密码与完整请求体 |
| 级别 | prod 默认 `info`；`debug` 仅临时开启且 2 小时内关闭 |
| 指标 | 请求量与时延（P50/P95/P99）、错误率、连接池、慢查询、CPU/内存/磁盘、对账差异数 |
| 健康检查 | `/actuator/health/liveness` 不查库；`/actuator/health/readiness` 查库 |
| 追踪 | `traceId` 贯穿前后端，错误页展示供报障 |
| 保留 | 日志 14 天、指标 90 天、审计日志 ≥1 年 |

**七条告警（必须配置）**：服务不可用（readiness 连续 3 次失败，P1）；5xx >1% 持续 5 分钟（P1）；P95 >1s 持续 10 分钟（P2）；磁盘 >85%（P2）；备份失败（P1）；结存对账差异 ≠0（P1，停止写入排查）；证书剩余 <14 天（P2）。

**备份**：托管数据库开自动备份与日志备份，保留 30 天，RPO ≤5 分钟；自建每日 02:00 `pg_dump -Fc` 上传 OSS，保留 30 天并开 WAL 归档；备份不与数据库同盘；每季度恢复演练并记录到 `RUN-002`。**没有演练过的备份等于没有备份。**

**配置与密钥**：`.env.defaults`（可入库）→ `.env.<env>`（不入库）→ 环境注入（prod 优先）；密钥随机 ≥32 字节、不复用、不入日志/镜像/仓库；应用账号只授 DML，迁移用独立账号；会话密钥每 90 天轮换；启动时校验必需变量，缺失快速失败。

**单人期实践**：发布窗口每周四 14:00–16:00，避开用餐高峰；重大节假日前 3 天至节后 1 天冻结；staging 用 prod 备份预演；蓝绿而非原地替换；发布后盯 30 分钟；回滚写成一键脚本。

### 7.5 关键约束

1. 禁止手工修改生产服务器上的代码或配置；紧急变更也须 24 小时内补回 PR。
2. 数据库与对象存储不得暴露公网；应用端口只监听内网。
3. 生产禁止长期开启 `debug`；响应不得返回堆栈。
4. 未配置告警的系统不算上线；未演练的备份不算备份。
5. 镜像只用固定 tag，禁止 `latest` 上生产。
6. 发布前必须有一次成功的全量备份，否则中止。
7. 通过 G5 即进入团体开发规范期，单人亦不例外（`DEV-010`）。

### 8.4 规范标准

**扩展启动规则**：G5 前不开发参考方向；上线后按"方向评估 → RFC → 立项"逐条推进；未过 RFC 不进 Roadmap、不进发布说明；扩展若破坏 U1 ~ U4 任一通用性，先做基础改造立项；同一轮最多推进一条扩展方向。

**节律**：两人以下每两周一个 minor（1.5 周开发 + 0.5 周收尾）；排期 30 分钟自定；每日 5 分钟写日志；周五自测与 UAT；回顾 30 分钟三问。多人时改为计划会、站会、演示会，节律不变。

**优先级**：唯一入口是 Issue。Must（数据错误、结存不准、安全问题、核心流程阻断）当前轮；Should（影响多数人效率、有绕行）下轮；Could（体验优化）Backlog；Won't（超出三条硬边界）关闭并说明。每轮承诺量 ≤ 上轮实际完成量的 80%。

**版本语义**（SemVer 2.0）：破坏性变更主版本 +1；向后兼容的新功能次版本 +1；缺陷修复修订 +1；预发布加后缀；0.x 阶段次版本可含破坏性变更，须在 `CHANGELOG` 标注。

**破坏性变更**：走 RFC 公示 ≥5 天；提供迁移指引；保留一个版本的兼容层；`CHANGELOG` 用 `⚠️ BREAKING` 单独成段。

**弃用**：公开接口或配置项弃用，须在至少一个 minor 中输出弃用警告并在文档标注 `deprecated since x.y`，下个主版本才移除。

**支持窗口**：最新 minor 全部修复，至下个 minor 发布 + 3 个月；上一个 minor 仅安全与 P0；更早版本 EOL，在 Releases 标注日期。

**Feature Flag**：引入（默认关）→ 灰度（内部账号）→ 全量（默认开）→ 稳定 ≥2 个 minor 后移除。flag 超过 2 个 minor 视为技术债，必须登账。

**五项度量**：发布频率（每月 ≥2 次）、变更失败率（<15%）、平均恢复时间（<1 小时）、缺陷逃逸率（<10%）、技术债偿还比（≥20%）。

**Release 格式**：`## vX.Y.Z (日期)` + 新增 / 修复 / 变更 / ⚠️ 破坏性变更（含迁移步骤）/ 升级指引 / 贡献者。贡献者段统一写 `The JamesHome Contributors` 并链到 `CONTRIBUTORS.md`，不列人名、不列模型名。

### 8.5 关键约束

1. 上线变更必须来自已合并的 PR，不存在"只在服务器上改过"的变更。
2. 每个 minor 更新 `CHANGELOG` 与版本号；版本号只由发布流水线执行。
3. 破坏性变更不得出现在修订版本中。
4. 同一轮不得同时做"大重构"与"大功能"。
5. 技术债预算不得被功能挤占；被挤占须在回顾中记录并下轮补回。
6. 扩展功能必须在 RFC 通过后立项。

# DEV-006 工程规范·总纲

这份文档回答一个问题：**这个仓库按什么标准运转、谁定、做到什么程度算完成，以及每一条标准落在哪份文件、哪段代码上。**

### 2.2 冲突顺序

1. **用词**：以 `GLOSSARY-001` 为准，任何文件不得另立口径。
2. **现实**：实现与规范不一致时，以 `DEV-007` 偏离台账记录的现状为准，但台账必须写明理由与收回条件。
3. **本套内部**：分册在各自领域内优先于总纲的概述；两者冲突视为缺陷，按 §8 修订，不得两处并存。
4. **专项文档**：`DEV-002` / `DEV-003` / `GOV-002` / `OPS-001` 在其主题内优先于本套的概述。
5. **GOV-000**：方法来源与历史基线，不作为验收依据；本套未覆盖而 GOV-000 有规定的，按 GOV-000 执行，并在下一轮回写本套。

### 2.3 GOV-000 的位置

GOV-000 保持原样，不改写、不迁入 `docs/`：

- **为什么不改写**：它是本项目的规则来源，附录 F 记录了 v1.4 ~ v1.12 的修订链。改写会让"某条规则从哪来"失去锚点。
- **为什么不整份搬入**：它覆盖 S0 ~ S6 全阶段，其中 S5 / S6 尚未进入；整份搬入会让未进入阶段的条款看起来已经生效，与"规范写了但没做"是同一种病。搬入的是**逐章落地后的版本**，不是摘要——对照表见 §7。
- **索引地位**：`INDEX-001` 将 GOV-000 登记为「指导文档」，`check-docs.mjs` 把 `GOV-000` 列入外部标识白名单，只校验引用、不校验文件。

## 3. 产品与边界

### 3.1 定位

面向**团体厨房**的**库存远程查看**系统——让不在厨房现场的人（负责人、采购、管理者）随时看到"现在有什么、还剩多少、哪些快没了"。

目标场景是为固定人群集中供餐的厨房。部署形态为公有云单机自托管（阿里云 ECS + 云数据库），不依赖专有中间件，不追求多云适配；具体规格待 S5 定稿（`OPS-001`）。

### 3.2 三条硬边界

| 边界 | 含义 | 本仓落点 |
|---|---|---|
| 非商业 | 不产生交易，不接入支付、结算、采购付款，不与任何资金流打通 | `SCOPE-001` Out 列；`GOV-005` 依赖清单中无支付类 SDK |
| 不改写现场作业 | 只做"记录—查看—统计"，不控制硬件，不自动生成采购单，不替代现场作业系统 | `SCOPE-001` Out 列；`PRD-001` 不做清单 |
| 不做组织集成 | 不绑定学校、企业或机构身份体系，不接入 OA / HR / 统一认证，账号自建 | `app_user` / `invite_code` 自建账号；无 SSO 依赖 |

定位一经 G0 确认即冻结。出现不适配的场景时，登记为**参考方向**（§3.6），而不是修改定位。

### 3.3 角色与权限

| 角色 | 权限范围 | 实现要点 |
|---|---|---|
| 管理员 `admin` | 全部读写 + 账号管理 + 单位字典维护 + 数据导出 | 用户、邀请码、重置密码、单位写操作仅此角色 |
| 记录员 `editor` | 物料建档与编辑、分类字典维护、出入库与盘点登记、红冲、查看统计 | 可写业务数据，不可管账号与单位 |
| 查看者 `viewer` | 只读：库存总览、物料详情、统计报表 | 任何写接口返回 403 |

权限模型为 RBAC + 资源级校验；MVP 只做角色级，接口层保留 `permission` 粒度扩展点。**只读是第一等公民**：viewer 的首屏速度与移动端可用性优先级不低于编辑功能。

实现处：`SecurityConfig` 按 HTTP 方法与路径分权；`/api/v1/stats/category-distribution`、`/api/v1/stats/top-out`、`/api/v1/reconcile` 仅 `admin`；`/healthz`、`/v3/api-docs*`、`/api/v1/invite-codes/validate` 匿名可访问。验证见 `PermissionMatrixTest` 与 `DEV-005` 第 10 条。

### 3.4 领域模型（八表）

| 实体 | 职责 | 关键字段（节选） |
|---|---|---|
| `material` | 物料主数据 | code、name、category_id、unit_id、spec、safety_stock、shelf_life_days、image_url、status、version、deleted_at |
| `material_category` | 分类字典 | name、sort_order、status |
| `unit` | 单位字典 | name、sort_order、status |
| `stock_movement` | 库存流水 | material_id、type、quantity、occurred_at、operator_id、note、reversal_of、reversed、created_at |
| `stock_balance` | 当前结存 | material_id、quantity、last_movement_at、version |
| `audit_log` | 操作审计 | actor_id、action、entity、entity_id、before、after |
| `app_user` | 账号 | username、display_name、role、status、password_hash |
| `invite_code` | 邀请码 | code、status、created_by、used_by、used_at |

另有 `SPRING_SESSION`、`SPRING_SESSION_ATTRIBUTES` 两张会话表（Spring Session JDBC），不属于领域模型。

**流水类型**：`IN`（入库）、`OUT`（出库）、`ADJUST`（盘点调整）、`REVERSAL`（红冲）。

**结存恒等式**：`结存 = Σ IN − Σ OUT ± Σ ADJUST − Σ REVERSAL 对应量`。每日 02:30 由 `ReconciliationService` 定时重算并与 `stock_balance` 比对，差异写日志；另提供 `GET /api/v1/reconcile` 供人工与测试查询。

**红冲机制**：错误流水不得编辑或删除，只能发起红冲——生成一条方向相反的 `REVERSAL` 流水，`reversal_of` 指向原流水，原流水标记 `reversed = true`；一条流水只能被红冲一次。数据库触发器 `trg_movement_immutable` 拒绝删除、只允许更新 `reversed`；`trg_movement_reversal_sign` 保证红冲方向与原流水相反。

### 4.2 为什么是 MyBatis-Plus

本项目近一半工作量在统计：窗口函数、按日分组、多表聚合。ORM 生成的 SQL 不可控，调优时看不到语句也改不动；MyBatis 把 SQL 摆在明面上，匹配这个特征。库存写入大量是单表 CRUD，`BaseMapper` 省掉样板。

代价同样写明：① 实体与领域对象须显式转换；② 多表查询靠手写 join，N+1 靠评审发现；③ 分页自 3.5.9 起需单独引入 `mybatis-plus-jsqlparser`，漏引只在运行期报错。三条都写进了 `DEV-008` §3.3。

### 4.3 版本纪律

- 版本号以 `backend/pom.xml`、`frontend/package.json`、`backend/.mvn/wrapper/maven-wrapper.properties` 为准，任何文档里的版本号与它们冲突时，以构建文件为准并回写文档。
- JDK 采用两级锁定：大版本（25）由 CI 与本机对齐；补丁号由本机环境决定，CI 允许同大版本最新补丁，实际版本记入当轮迭代记录。
- JaCoCo 0.8.12 与 google-java-format 1.24.0 在 JDK 25 下不可用（无法解析 class 文件 major 69；javac 内部 API 变更），实际采用 0.8.16 / 1.29.0。这是 `DVT-01`、`DVT-02`，不是笔误。
- 新增运行时依赖须满足许可证白名单（Apache-2.0 / MIT / BSD / EPL），版本统一在父 POM 声明。

### 4.4 运行环境

S5 尚未开启，生产环境未定稿。仓库内已有两份骨架：`infra/compose/compose.prod.yml`（api / web / caddy 三服务、健康检查、固定 tag）与 `infra/caddy/Caddyfile`（TLS、安全响应头、`/api` 与 `/actuator` 转发）。拓扑、规格、备案与备份策略见 `OPS-001` / `RUN-002` 草案，S5 定稿后本节的"未定"改为实际值。

## 8. 规范维护

| 项 | 规则 |
|---|---|
| 谁能改 | 开发者审定；模型只能起草并标 `in_review` |
| 何时改 | 阶段推进、工具链变更、门禁增删、偏离收回、季度复核 |
| 怎么改 | 开 issue 或 RFC → 改文档 → `node scripts/check-docs.mjs` → 写当轮迭代记录 → PR → 审定 |
| 删除条款 | 必须给出替代方案或"不再适用"的理由，并在变更记录保留原条目 |
| 到期复核 | `next_review` 到期后人工复核；自动标记未实现（见 `DEV-008` §2.10） |
| 与实现冲突 | 先登 `DEV-007`，再决定改实现还是改规范；不得静默改规范迁就实现 |

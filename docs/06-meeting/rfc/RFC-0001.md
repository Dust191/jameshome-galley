# RFC-0001 收窄禁用写法并拆分易混提示

这份文档回答一个问题：**为什么现在的用词反查拦不住真问题，以及改哪一处能拦住。**

- **状态**：resolved
- **类型**：全局口径变更（G-6）

## 1. 摘要

glossary 的「禁用写法」一列同时装着两种东西：真正会造成概念漂移的词（如"存量"之于"结存"），和在任何语境都正常的泛用词（如"验收""评审"）。混装的结果是反查失去意义——26 条告警里只有 6 条是真的。

本 RFC 提议：**把一列拆成两列**，「禁用写法」只放"出现即错"的词并升级为 CI 硬门禁；新增「易混提示」存放语境相关词，只告警不阻断。

## 2. 现状

对 35 份文档做反查，29 个禁用写法命中，26 条告警。按命中文件数：

| 禁用写法 | 命中文件数 | 来自词条 | 性质 |
|---|---|---|---|
| 验收 | 10 | 审定回顾 | 泛用 |
| 修正 | 9 | 盘点调整 | 泛用 |
| approve | 8 | 审定回顾 | 泛用 |
| 例外 | 7 | 偏离登记 | 泛用 |
| 偏差 | 6 | 偏离登记 | 泛用 |
| 用例 | 6 | 用户故事 | 泛用（"测试用例"是另一个概念） |
| 评审 | 5 | 审定回顾 | 泛用 |
| 用户 | 5 | 账号 | 泛用 |
| 迭代 | 4 | 轮次 | 泛用（名词性固定说法不受限，已由开发者明确） |
| 改密 | 4 | 密码重置 | 泛用 |
| 类别 / 算法 / 入账 | 各 3 | 分类 / 口径 / 入库 | 泛用 |
| 存量 / 库存量 / 领用 / 发出 / 品类 / 单据 | 1 ~ 2 | 结存 / 出库 / 分类 / 流水 | **真漂移** |

## 3. 问题定性

一个字段承担了两个语义，导致三种后果：

1. **门禁不可用**：真漂移会被噪音淹没，只能降级为人工抽检（G2 第 4 项当前就是这么过的）。
2. **规则反噬**：写作者开始绕词——不写"验收通过"改写"核对无误"，用词反而更不统一。
3. **维护意愿下降**：每轮都看到 20 多条"错误"，久了就没人看了。

## 4. 方案对比

| 选项 | 做法 | 代价 | 能否恢复门禁 |
|---|---|---|---|
| A 收窄 | 泛用词移出禁用列，只留真漂移 | 词条要改；泛用词失去记录位置 | 能 |
| B 维持 | 保持"告警不阻断" | 零成本 | 不能 |
| C 分域 | 按 `所属域` 分流：领域类硬拦、流程类只提示 | 需改脚本；同一词条仍混装 | 部分 |
| **A + C（推荐）** | 拆列 + 按列决定阻断或提示 | 改表结构 + 改脚本 + 改词条 | **能** |

推荐 A + C：拆列解决"混装"，按列处理解决"阻断"，两者互补。

## 5. 详细设计

### 5.1 表结构

词条表由 8 列扩为 9 列：

| 列 | 语义 | 校验行为 |
|---|---|---|
| 禁用写法 | 出现即错，无例外 | **CI 失败** |
| 易混提示（新增） | 语境相关，提示人工确认 | CI 告警，不阻断 |

无任何词条时填 `—`。

### 5.2 词条调整

保留在「禁用写法」（真漂移，硬拦截）：

| 词条 | 保留 | 理由 |
|---|---|---|
| 结存 | 存量、库存量、余量 | 同义替换直接改变概念 |
| 出库 | 领用、发出 | "领用"是现场口语，与出库不是同一动作 |
| 分类 | 品类 | 品类是另一层概念 |
| 流水 | 单据 | 单据常指凭证，不是流水 |
| 团体厨房 | 中央厨房 | 中央厨房是集中生产模式，与本项目定位相反 |
| 契约 | 接口文档 | 接口文档常指说明性文字，不是可校验的契约 |
| 种子数据 | 测试数据 | 测试数据泛指，无法复现 |
| 轮次 | 周期、sprint | 周期是时间概念，不是变更单元 |
| 账号 | 用户名 | 用户名与账号名混用会造成登录语义不清 |
| 查看者 | 只读用户 | 角色名与描述性说法混用，权限矩阵会读串 |

移入「易混提示」（语境相关，只提示）：

| 词条 | 移出 | 原因 |
|---|---|---|
| 审定回顾 | 验收、评审、approve | "验收"另有"阶段门验收"，不能一概禁 |
| 账号 | 用户、登录名 | "用户故事""用户"在 PRD 语境正常 |
| 轮次 | 迭代 | 仅动词用法受限，名词"迭代记录"合法 |
| 盘点调整 | 修正 | "修正"是通用动词 |
| 偏离登记 | 例外、偏差、豁免 | 三者都是通用词 |
| 用户故事 | 用例 | "测试用例"是另一概念 |
| 密码重置 | 改密 | UI 文案常用 |
| 分类 | 类别 | 通用词 |
| 口径 | 算法 | 讨论实现时"算法"合法 |
| 入库 | 入账 | 技术债台账用"入账"，语义不同 |
| 硬边界 / 红线 | 底线 | 通用词 |

合计调整 13 条词条，其中 10 条保留部分禁用词、11 条新增易混提示（有重叠）。

### 5.3 校验规则

| 规则 | 现状 | 改后 |
|---|---|---|
| 禁用写法命中 | 告警 | **失败**（CI 红） |
| 易混提示命中 | 无 | 告警 |
| 词条内部掩码 | 已有 | 保留（"迭代记录"不触发"迭代"） |
| `term-check: off` | 已有 | 保留（仅限分析类文档，须写明理由） |

### 5.4 配套文档改动

| 文档 | 改动 |
|---|---|
| `GOV-000` §4.4.1 | 词条字段由 8 项改为 9 项，说明两列的校验差异（升 v1.11） |
| `GOV-000` §4.4.1 G- 规则 | 新增一条：易混提示不构成违规，但使用后须人工确认 |
| `GLOSSARY-001` §1 | 使用规则增加同样一条 |
| `DEV-004` | TD-03（反查降级）标记为已偿还 |

## 6. 迁移

1. 先加列，把 13 条词条的泛用词搬到新列（一次性脚本改名，不手改）；
2. 跑一次全量校验：期望「禁用写法」零命中、「易混提示」26 条左右告警；
3. 若禁用列仍有命中，逐条判断是文档该改还是词条该调；
4. 之后 CI 才把禁用列升级为失败。

**历史文档不批量改写**：ITER 类记录是历史，只增不改；命中的当轮记录在遗留项里说明即可。

## 7. 影响面

| 面 | 说明 |
|---|---|
| 术语表 | 结构变更，48 条词条全部要检查新列是否有值 |
| CI | guards job 的文档校验从"全告警"变为"禁用列失败 + 易混列告警" |
| 写作 | 作者需要区分"不能写"和"注意别混" |
| 不涉及 | 代码、接口、数据模型 |

## 8. 风险与回退

| 风险 | 应对 |
|---|---|
| 拆列时把真漂移词误移出去 | 逐条列表在 §5.2，审查时可逐行否决 |
| 升级为失败后历史文档被卡 | 迁移第 2 步先跑全量，确认禁用列零命中再升级 |
| 新增列让表格过宽 | 易混提示列可放多个词，用顿号分隔，不换行 |

回退：保留旧列内容于 `git history`；若升级后频繁误报，把 CI 规则改回告警即可，无需改数据。

# GOV-007 模型偏离记录

这份文档回答三个问题：模型在哪些地方没按规范做、当时怎么处理的、以后靠什么不再犯。

## 1. 为什么单独立账

现有三本账都不承载这件事：

| 台账 | 记的是 | 为什么不合适 |
|---|---|---|
| `DEV-007`（`DVT`） | 规范与实现不一致 | 那是工程事实，不是执行过程 |
| `DEV-004`（`TD`） | 已知未偿的技术债 | 债是“以后要还的功能/质量缺口”，不是“这次没照做” |
| `ITER` | 本轮做了什么 | 偏差散在各轮里，下一轮就被淹没，看不出重复 |

结果是同一个错误反复出现却没人统计：提交信息的 scope 已经错了两次，迭代记录的必填节漏了七份，每次都是被指出后当场修补，修完不留痕，下一轮照旧。

本台账只做一件事：**把“模型没按规范执行”变成可计数、可追溯、可闭环的条目。**

## 2. 什么算模型偏离

同时满足三条才入账：

1. 规范里有明确要求（`DEV-006` ~ `DEV-009`、模板、`GOV` 系列）；
2. 本轮产出未满足该要求；
3. 能指出具体条款与具体产出（文档路径、提交、命令）。

不算的三类：

| 情形 | 去处 |
|---|---|
| 规范没写，只是“更好的做法” | 提 RFC 或写进下一轮建议，不入账 |
| 需求变更导致的返工 | 记 `ITER`，不入账 |
| 环境限制导致做不到（本地无法完整构建镜像、网络受限） | 记 `ITER` 遗留，不入账 |

## 3. 记录规则

- **谁写**：模型在发现当轮即写；开发者发现时可要求补录，模型不得以“影响不大”为由省略。
- **何时**：与该轮 `ITER` 同批提交，不后补、不攒批。
- **编号**：`MDV-NN`，按**发生顺序**，不复用、不重排。
- **只增不改**：已登记条目不改写。事实有误或状态变化，追加「补记」或在「状态」列更新，并在 §9 留痕。
- **闭环判据（重要）**：现象已修 **且** 防止复发的机制已落地（校验、模板、门禁、自动化之一）。只修现象不加机制，状态一律写「未闭环」。
- **追溯**：台账建立前的案例只登记有书面依据的（`ITER`、提交记录、提交信息、记忆文件），不凭印象补。

## 4. 条目字段

| 列 | 含义 |
|---|---|
| 编号 | `MDV-NN` |
| 日期 | 发生日期 |
| 轮次 | 对应 `ITER` 编号；跨轮写区间 |
| 违反条款 | 文件与节号，精确到可核对 |
| 现象与影响 | 做了什么、造成什么后果；没有实际影响也要写明 |
| 发现方式 | CI / 开发者指出 / 模型自查 / 事后核查 |
| 处置 | 已采取的动作，含提交号 |
| 状态 | 已闭环 / 未闭环（附一句缺口） |

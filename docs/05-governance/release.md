# GOV-002 发布流程

这份文档回答一个问题：**什么算一个版本、发版前必须做齐哪几件事。**

## 1. 版本号

遵循语义化版本 `主.次.修`：

| 位 | 变更含义 | 举例 |
|---|---|---|
| 主 | 不兼容的对外变更 | `1.0.0 → 2.0.0` |
| 次 | 向后兼容的新功能 | `0.1.0 → 0.2.0` |
| 修 | 向后兼容的缺陷修复 | `0.1.0 → 0.1.1` |

`0.x` 期间允许破坏性变更出现在"次"位，这是语义化版本对未定型软件的通例；一旦发布 `1.0.0`，规则收紧到标准语义。

**当前阶段与版本对应**（GOV-000 §1.2）：

| 阶段 | 版本 | 状态 |
|---|---|---|
| S1 骨架 | 0.0.1 | 已达成 |
| S2 文档体系 | 0.0.2 | 已达成 |

## 2. 发布前清单

八项全绿才允许打标签，缺一即不发：

| 序 | 项 | 判据 |
|---|---|---|
| 1 | CI 全绿 | 最近一次 main 的流水线通过 |
| 2 | 文档同步 | 本轮改动的接口/表结构已在 DES 更新 |
| 3 | ITER 已审定 | 本轮 ITER 的审定结论非空、非"驳回" |
| 4 | 技术债检查 | `DEV-004` 已更新，新增债务入账 |
| 5 | 数据库迁移可回退 | 按 `DEV-002` §6 拆分，或已确认无需回退 |
| 6 | 备份可用 | `RUN-002` §2 最近一次备份校验通过 |
| 7 | 冒烟用例 | 三条 E2E 通过（S3 起） |
| 8 | CHANGELOG | 已按 §3 格式补齐当日条目 |

## 3. CHANGELOG

采用 Keep a Changelog 的分组，按版本倒序：

```markdown
## [0.1.0] - 2026-12-01
### 新增
- 物料建档与出入库登记
### 变更
- 结存改为按流水实时求和
### 修复
- 红冲后统计笔数未回退
### 移除
- 盘点差异率指标（改由人工报表承担）
```

规则：

- 只写**面向使用者**的变化，内部重构不入 `新增`。
- 每条以动词开头，一句话说清"变了什么"，不写"优化若干问题"。
- 版本号与 `git tag` 完全一致，标签格式 `v0.1.0`。
- 发布后不再修改已发布版本的条目；发现错误只能在新版本更正。

## 4. 打标签与发布

```bash
git tag -a v0.1.0 -m "MVP：物料、流水、统计"
git push origin v0.1.0
```

- 标签只能打在 `main` 上，`hotfix` 分支打补丁版本（如 `v0.1.1`）。
- 预发布用 `v0.2.0-rc.1`，`rc` 不计入 `CHANGELOG` 的正式版本段落，合并进正式版后统一记录。
- 标签一旦推送不得移动或删除；发现打错只能废弃并递增补丁号。

## 5. 紧急修复

生产缺陷允许走快车道，但不豁免记录：

1. 从最新标签切 `hotfix/<版本>`；
2. 只修该缺陷，不夹带其它改动；
3. 修完回 `main` 同步（`git cherry-pick`）；
4. 发布补丁版本，`CHANGELOG` 记入"修复"；
5. 事故记录写入 `RUN-001` §7。

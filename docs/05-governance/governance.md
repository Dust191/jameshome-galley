# GOV-001 治理模型

这份文档回答一个问题：**谁能做什么决定，出分歧时听谁的。**

根文件 `GOVERNANCE.md` 是面向外部读者的简版；本文是面向维护者的完整版，两者冲突时以本文为准并回头修 `GOVERNANCE.md`。

## 1. 角色

| 角色 | 权限 | 现状 |
|---|---|---|
| 维护者（Maintainer） | 合并 PR、发版、裁决争议、任命贡献者 | 1 人（`@Dust191`） |
| 贡献者（Contributor） | 提交 PR、参与讨论、认领任务 | 0 人 |
| 使用者（User） | 提 Issue、使用软件 | 未公开 |

**单人期（当前）**：维护者同时是唯一决策主体与责任主体，模型承担起草与核对，不承担决策（见 GOV-000 §0.4 H1）。

## 2. 决策机制

按影响面分三档，档位决定留痕方式：

| 档 | 适用 | 载体 | 生效条件 |
|---|---|---|---|
| 日常 | 实现细节、文案、测试 | ITER 的变更清单 | 维护者自审即可 |
| 结构调整 | 目录、依赖、构建、CI | ADR + ITER | ADR 状态 `accepted` |
| 全局口径 | 术语、指标、数据模型、对外承诺 | RFC + ITER | 维护者书面确认，且 RFC 归档 |

**RFC 流程**：提出（`docs/06-meeting/rfc/RFC-NNNN.md`）→ 说明选项与代价 → 维护者裁定 → 结论回写相关文档 → 归档，不删除。

## 3. 冲突解决

| 情形 | 处置 |
|---|---|
| 文档与实现不一致 | 以文档为准，先修实现；若文档本身错了，走 RFC 改文档，不直接改代码迁就 |
| 两份文档冲突 | 以编号更"上游"的为准：PRD > DES > DEV > OPS；仍不能判定时由维护者裁定并记录 |
| 模型与开发者意见不一致 | 以开发者为唯一决策者；模型保留意见写入 ITER 的"逐项核对意见" |
| 外部贡献者与维护者分歧 | 在 Issue 中公开讨论；维护者有最终裁定权，但须给出理由 |

## 4. 代码所有权

- `CODEOWNERS` 指向维护者，任何 PR 至少 1 名维护者批准。
- 单人期以本地模拟 PR 替代（`DEV-002` §5），扩编即恢复真实 review。

## 5. 扩编路径

出现第二位稳定贡献者时，按顺序恢复：

1. 开启 `main` 分支保护与强制 review；
2. 关闭本地模拟 PR 例外，记录失效日期；
3. 新贡献者经 3 个合并 PR 后可被提名为维护者；
4. 维护者人数 ≥2 后，重大决策改为"至少 2 人同意"。

## 6. 治理变更

修改本文或 `GOVERNANCE.md` 须走 RFC，并在 `CHANGELOG.md` 记录。治理规则不得通过"惯例"悄悄改变——没有记录的变更视为未发生。
